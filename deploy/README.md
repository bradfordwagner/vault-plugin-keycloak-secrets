# Seeding the engine's admin config (deployer contract)

The engine authenticates to Keycloak as one **confidential admin client** (see
[`../docs/admin-client.md`](../docs/admin-client.md)). Before it can vend
credentials, `<mount>/config` must be written **once** with that client's secret.
The secret is generated by Keycloak and must **never** live in git.

This directory is a **contract**, not a runnable manifest: it describes what a
deployer must provision. A concrete deployment (Job, Helm hook, etc.) belongs in
your platform's GitOps/config repo, wired to your clusters — not here, so no
cluster-specific values or credentials leak into this public repo.

## What must happen

Write `<mount>/config` with the admin connection + secret:

```sh
vault write <mount>/config \
  server_url=<keycloak-base-url> \
  auth_realm=master \
  client_id=<admin-client-id> \
  client_secret=<seed value from Keycloak> \
  rotation_period=720h
```

- `server_url` is whatever address the **Vault server** can reach Keycloak's
  Admin REST API on. In-cluster this is typically the internal Service DNS name
  (e.g. `http://keycloak.<ns>.svc:8080`), so there is usually **no per-environment
  hostname** to template.
- `rotation_period` is optional but recommended — see [Rotation](#rotation-is-automatic).

## The seed is transient by design

The admin secret is **never held long-term by a human**. Once `rotation_period`
is set, the engine regenerates the admin secret in Keycloak on the **first tick**
(within ~a minute of seeding) and stores the new value itself. So:

- the human-supplied `client_secret` is purged almost immediately;
- any copy of it you staged for the seed (a Kubernetes Secret, kv-v2 entry, etc.)
  goes **stale** right after and should be treated as one-shot bootstrap material,
  not steady-state config.

Make the seed **idempotent** so it is safe to re-run and safe to leave applied —
it must not clobber a secret the engine has already rotated:

| situation                     | seed action              |
| ----------------------------- | ------------------------ |
| `config` already has a secret | exit `0`, write nothing  |
| `config` unset (first seed)   | write it, exit `0`       |
| cannot configure (any reason) | exit `1`                 |

`config` reads never return the secret — only `client_secret_set` (plus
`rotation_period` / `last_rotated`), which is exactly the field an idempotent seed
short-circuits on:

```sh
vault read -field=client_secret_set <mount>/config   # "true" once seeded
```

## Vault access the seeder needs

A Kubernetes-auth role (or equivalent) whose token carries a policy granting
**write on the config path only** — least privilege; nothing else is required:

```hcl
# policy: keycloak-plugin-seed
path "keycloak/config" {
  capabilities = ["create", "update", "read"]
}
```

`read` is included solely for the idempotency short-circuit above; it never
exposes the secret. Do **not** grant this identity anything on
`keycloak/realm/*` or `sys/*` — role management and mounting are owned by other
identities (e.g. a plugin manager).

## Rotation is automatic

Once seeded with `rotation_period`, rotation is hands-off. To purge the seed
secret immediately instead of waiting for the first tick — or on suspected
exposure — force a rotation (break-glass):

```sh
vault write -f <mount>/config/rotate
```

## One config serves every realm

You do **not** seed per realm. The single admin credential administers every
realm; grant it each realm's management roles (see
[`../docs/admin-client.md`](../docs/admin-client.md)) and define roles under
`<mount>/realm/<realm>/roles/...`.
